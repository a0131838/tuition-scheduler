# TASK-20260819：后台读取性能第二阶段

## 目标

解决工单与 AI 接入后多个后台页面等待时间变长的问题，同时严格保留原排课、工单、课时、课包、考勤、工资、财务和通知业务规则。

## 根因证据

1. 后台共享布局在每次切换页面时都会计算完整审批收件箱，即使当前页面与审批无关。
2. 同一次服务端渲染中，布局、语言和页面会重复读取同一个员工会话。
3. 签到告警打开页面时同步扫描 60 天数据，页面必须等待同步结束。
4. 月课表、工单详情和今日工作台存在可以并行却串行等待的独立读取；工单详情还会串行等待 AI OS 和正式课表。
5. 新加坡到远程数据库首次连接约 0.68 秒、热连接约 0.04 秒，因此重复或串行查询会明显放大页面等待。

## 实施内容

- 共享导航不再读取完整审批汇总；审批中心本身继续实时读取原数据源。
- 员工身份只在同一个 React Server Components 请求内按会话令牌复用，不做跨请求权限缓存。
- 签到告警同步放到响应后执行；当前已存在的告警立即展示，下一次刷新看到同步后的结果。
- 月课表数据与排课活动、工单 AI 方案与正式课表、今日工作台相互独立的查询并行启动。
- 保留现有加载反馈、50 条分页、AI 2.5 秒超时、人工手动处理入口和全部正式执行校验。

## 明确不改

- 不修改排课、改课、取消、换老师及冲突判断。
- 不修改课包余额、扣课、考勤、老师工资、财务或通知逻辑。
- 不修改数据库结构和真实业务数据。
- 不修改小程序包。
- 不让 AI 在普通后台导航时运行，也不让 AI 绕过人工确认。

## 正式环境复测发现与补充修复

工单筛选请求本身约 0.38 秒，但旧按钮把等待状态绑定在“网址查询参数发生变化”上。重复应用同一筛选或应用空筛选时，网址可能不变，导致按钮一直显示“正在筛选”。此外，空筛选与首次进入页面无法区分，会错误恢复上次记忆的状态。

- 主筛选表单改用真实路由 transition 控制等待状态，请求结束即恢复。
- 每次人工应用筛选都写入 `applyDesk=1`，明确阻止本次空条件被历史筛选覆盖。
- 不改变筛选字段含义、工单数据或任何正式业务规则。
- 修复后再次通过 180/180 后台回归、6/6 性能结构回归、251 页生产构建和差异检查。

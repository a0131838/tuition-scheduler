## 1. 项目目标

这个项目分成两条线，但不能用同一种产品思路处理。

1. 员工端：让国内员工、老师、教务、客服、财务可以在手机上处理高频任务。
2. 家长/学生端：让家长持续看到孩子在新加坡的学习、生活、学校事务和机构跟进状态，降低不确定感和焦虑。

核心判断：

- 员工端不是把整个后台原封不动搬进小程序，而是做“移动任务台”。
- 家长端不是简单展示课表，而是做“学业管家交付界面”。
- 当前系统已有课表、出勤、课后反馈、学业管理字段、结课报告、工单、家长可用时间收集等基础，第一阶段应尽量复用。
- 家长端要覆盖普通课程、学业管理、全程托管三类学生；普通课程也要提供清晰透明的家长体验，形成与其他机构的差异。
- 课后反馈第一版按“老师提交后直接发布”处理，但内部仍要保留质量检测、撤回和补充说明能力。
- 家长端第一版包含课包余额和财务信息，因此权限、口径和数据解释必须单独设计。

## 3. 产品边界

### 3.1 第一阶段要做

员工端：

- 今日待办简版
- 学生搜索与学生详情简版
- 老师我的课次、提交反馈、可用时间、通知确认
- 工单查看与轻量更新
- 简单审批提醒
- 全角色移动入口：老师、教务、学管/客服、销售、财务、管理层都要能登录并看到自己的高频任务

家长端：

- 家长登录/绑定学生
- 孩子状态总览
- 未来课表和历史出勤
- 课后反馈时间线
- 阶段报告/月报
- 家长提交请求或意见
- 请求处理状态查看
- 课包余额、账单、付款、收据等财务信息摘要

### 3.2 第一阶段不要做

员工端暂不搬迁：

- 复杂财务报表
- 批量导出
- 课程/校区/教室/老师复杂配置
- EduTrust 课程文件配置
- 合同模板配置
- 大屏表格型后台

家长端暂不开放：

- 内部备注
- 老师/教务内部评价
- 复杂课包扣费明细的内部计算过程
- 内部风险原文
- 员工处理过程中的争议记录

## 4. 推荐技术路线

根据 2026-07-09 的确认，第一版目标改为原生微信小程序。移动 Web 仍可作为备用方案或内部调试入口，但不作为主路线。

### 路线 A：移动 Web MVP

做法：

- 继续使用现有 Next.js 系统。
- 新增 `/parent` 家长端页面和 `/admin/mobile`, `/teacher/mobile` 员工移动入口。
- 可用企业微信、微信浏览器、或微信小程序 WebView 承载。

优点：

- 最快验证。
- 最大程度复用当前数据库、权限和业务逻辑。
- 不需要一开始维护两套前端。

缺点：

- 体验不如原生微信小程序。
- 微信登录、订阅消息、文件能力受限制。

建议：作为备用路线，不作为当前第一版主路线。

### 路线 B：原生微信小程序

做法：

- 使用微信小程序前端。
- Next.js 提供 API。
- 微信 openid/手机号绑定家长账号。

优点：

- 用户体验更像真正小程序。
- 能用微信订阅消息、登录、手机号能力。

缺点：

- 需要补完整 API 层。
- 发布审核、权限、安全、前后端双维护成本更高。
- 如果产品方向未验证，容易做重。

建议：作为当前主路线推进。为了降低风险，第一版小程序仍要控制功能边界，不能把完整后台一次性搬进去。

### 4.1 原生小程序从零开始步骤

注意：小程序注册、认证、类目、审核规则可能变化，正式操作前需要再查微信官方最新说明。

## 6. 家长端信息架构

### 6.1 首页：孩子状态总览

首屏建议展示：

- 学生姓名、学校、年级
- 服务类型：普通课程 / 学业管理 / 全程托管
- 当前状态：正常 / 需关注 / 高关注

- 负责人
- 最近一次更新
- 下一节课
- 本月已上课次数
- 未读课后反馈数量
- 需要家长配合的事项

### 6.2 课表

展示：

- 未来课程
- 课程时间
- 课程名称/科目
- 老师
- 上课方式：线上/线下
- 地点或链接
- 状态：正常 / 已请假 / 已取消 / 待确认

第一阶段不建议让家长直接改课。改课请求通过“提交请求”进入工单。

### 6.3 课后反馈

展示：

- 本节课重点
- 目前发现
- 课堂表现
- 下一步计划
- 家长需要知道
- 作业
- 老师
- 上课日期

发布规则：

- 老师提交后默认直接发布给家长。
- 系统保留质量检测，发现过短、过泛或缺少下一步计划时提醒内部。
- 教务/学管可撤回、补充说明或要求老师修正。
- 家长端显示正式反馈内容，不显示内部质量评分和处理备注。

### 6.4 学业管家月报

面向学业管理和全程托管学生。

内容建议：

- 本月课程概览
- 本月学习进展
- 当前瓶颈
- 风险变化
- 老师反馈摘要
- 学校事务进展
- 生活/适应观察
- 下月计划
- 家长需配合事项

生成方式：

- 系统自动拉取课表、出勤、课后反馈、学生档案、工单。
- 学管人工编辑和确认。
- 管理者或负责人发布给家长。

### 6.5 家长请求

请求类型：

- 排课/调课
- 请假/取消
- 老师沟通
- 学校事务
- 学习状态咨询
- 生活适应
- 申请服务
- 续费/账务
- 投诉/建议

处理方式：

- 家长提交后自动进入现有 Ticket 工单。
- 内部按负责人和状态处理。
- 家长端只展示简化状态：已收到、处理中、等待家长补充、已完成、已关闭。

优先级最高：

- 今日待办

## 9. 权限与安全原则

1. 家长只能看到自己绑定的学生。
2. 家长不能看到内部备注。
3. 家长不能看到未发布的内部托管更新、内部工单详情和内部风险备注。
4. 课后反馈第一版默认直接发布，但必须支持撤回、补充说明、质量提醒和内部追踪。
5. 所有家长查看、提交、下载动作应记录审计。
6. 家长请求进入工单后，内部处理细节不完整暴露，只同步简化状态。
7. 家长端下载报告、查看合同、查看附件必须使用权限校验，不只依赖 URL 猜不到。
8. 小程序 API 必须和后台权限隔离，不能复用 admin 权限判断。
9. 财务信息只展示家长能理解的摘要：课包余额、账单状态、付款状态、收据状态；内部审批、修复、成本和合作方结算不展示。
10. 普通课程、学业管理、全程托管使用同一个家长端入口，但展示深度不同。

## 13. 风险清单

| 风险 | 影响 | 规避方式 |
| --- | --- | --- |
| 直接搬后台到小程序 | 成本高、体验差、维护难 | 只做高频任务台 |
| 家长看到内部备注 | 沟通事故 | 家长可见发布层 |

| 家长请求没有闭环 | 反而增加焦虑 | 接入 Ticket 状态 |
| 月报太依赖人工 | 运营负担大 | 系统自动草稿 + 人工确认 |
| 原生小程序第一版投入较大 | 开发、审核、维护成本更高 | 控制第一版边界，先做核心闭环 |
| 权限设计不独立 | 数据泄露风险 | 独立 Parent 权限体系 |
| 课后反馈直接发布 | 低质量或不当表达会被家长立即看到 | 五段式模板、质量检测、撤回/修正、老师培训 |
| 财务信息开放 | 家长误解课包、账单或付款状态 | 展示摘要和解释口径，不展示内部过程 |

model ParentAccount {

## 14.3 家长绑定方式说明

绑定失败风险来自“系统里的家长信息”和“家长实际登录信息”不一致。

手机号绑定的风险：

- 系统里可能没有录家长手机号。
- 系统里手机号可能是旧号码、少国家区号、格式不统一。
- 一个家长可能有多个孩子。
- 一个学生可能有爸爸、妈妈、监护人多个联系人。
- 中国手机号和新加坡手机号格式不同。
- 家长用微信登录时授权到的手机号，可能不是系统里登记的手机号。

邀请码绑定的优势：

- 管理员给某个学生生成邀请码或二维码。
- 家长扫码后绑定到指定学生，不依赖系统里手机号是否完全一致。
- 适合第一版快速上线和降低客服处理成本。

建议第一版流程：

1. 管理员在后台给学生生成家长邀请码/二维码。
2. 家长微信扫码进入小程序。
3. 家长确认学生姓名。
4. 家长填写手机号作为联系方式。
5. 系统完成绑定。

当前决策：

- [x] 第一版采用“邀请码/二维码优先 + 手机号补充”。
- [x] 手机号不作为第一版唯一绑定依据。

手机号的用途：

- 作为后续登录辅助和身份校验。
- 作为家长联系资料。
- 不作为第一版唯一绑定依据。

1. 家长继续在微信群说需求、投诉、请假、调课、财务疑问或给老师的话。
2. Emily 在员工小程序或后台点击“代家长创建工单”。
3. Emily 选择学生、请求类型、来源微信群、紧急程度、原话摘要，并可上传聊天截图。

6. 家长小程序只展示整理后的处理状态和结果，不展示内部沟通原话和内部备注。

建议新增功能优先级：

1. 员工端“代家长创建工单”：比继续强化家长自主提交更优先。
2. 工单来源字段：微信群、家长小程序、电话、线下、老师转达、内部发现。
3. 微信群截图/附件上传：支持 Emily 直接上传聊天截图作为证据。
4. 原话与对外摘要分离：内部可保存家长原话，对家长端只显示整理后的正式描述。
5. 快捷模板：请假、调课、投诉、财务问题、给老师的话，减少 Emily 录入负担。
6. 家长端状态同步：家长不必提交，但可以看到“已收到/处理中/等待补充/已完成”。

暂不建议第一版做：

- 自动读取微信群聊天记录。
- 机器人自动抓取家长消息。
- 要求家长必须在小程序内重新提交。

原因：

- 微信群自动读取涉及合规、技术权限和误识别风险。
- 真实业务里，人工判断家长话里的重点仍然必要。
- 第一版要先降低 Emily/Eva 的重复沟通成本，而不是改变家长习惯。

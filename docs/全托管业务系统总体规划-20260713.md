## 1. 业务愿景

全托管不是简单的补课、排课或家长客服，而是一项长期结果管理服务：家长或成年学生把一段教育与成长过程交给公司，公司持续负责规划、协调、执行、监督、预警和汇报。

系统最终应回答六个核心问题：

1. 这个学生现在处于什么阶段？
2. 公司承诺为他提供哪些服务？
3. 当前目标、风险和下一步动作是什么？
4. 最近公司、学校、老师、学生和家长分别做了什么？
5. 哪些承诺或截止日期即将逾期？
6. 家长或成年学生能看到什么正式交付结果？

目标不是把所有信息堆进学生备注，而是把全托管从依赖员工个人记忆的服务，升级为可交接、可追踪、可审核、可汇报、可规模化的业务系统。

## 2. 已确认业务口径

### 2.1 服务对象

- 大学前学生：父母将孩子交给公司，公司负责对接学校、管理学习、协调重要事务并进行阶段汇报。
- 大学阶段学生：继续管理学业发展、能力建设和成长目标。
- 大学及毕业阶段学生：提供实习、工作申请、面试、入职及后续发展安排。
- 服务会跨越多个阶段，同一学生可能先购买大学前托管，之后再购买大学成长管理或职业启航服务。

### 2.2 服务产品方向

1. `大学前全程托管`：学校对接、学习监督、考试与升学、生活适应、风险处理、家长汇报。
2. `大学阶段成长管理`：学业进度、选专业或转学、项目活动、科研、能力建设和实习准备。
3. `职业启航服务`：职业定位、简历、机会管理、申请、面试、Offer、入职和实习反馈。

### 2.3 系统建设原则

- 保留现有排课、考勤、课时包、反馈、期中/期末报告、财务、工单和家长小程序功能。
- 全托管能力采用新增模块和关联数据的方式建设，不直接改写已有结算、排课、扣课、老师工资或报告口径。
- 不把长期托管记录全部塞进 `Student.note`。
- 不把通用 `Ticket` 当成全托管主档案；工单用于处理请求和异常，托管时间线用于记录连续服务。
- 不改造现有 `MidtermReport` 和 `FinalReport` 来冒充托管月报；托管报告应是独立报告类型。
- 成年学生的个人信息和家长可见权限必须单独设计，不能默认学生成年后家长仍可查看全部内容。

### 2.4 全托管价值主张

已确认的核心定位：`专业的事情交给专业的人做`。

目标家长通常面临以下困难：

- 语言沟通存在障碍，不能顺畅理解学校通知、会议和老师反馈。
- 不熟悉国际课程、选课、考试、升学路径和学校运行规则。
- 不知道孩子真实的学习状态，也不知道哪些问题需要立即介入。
- 即使已经陪读或安排寄宿家庭，也缺少专业的学业判断和长期规划。
- 在孩子没有陪读家长时，对学校、学习、生活状态和突发情况更加焦虑。

因此，全托管服务的核心承诺不是保证成绩、录取或工作结果，而是：

1. 持续收集学校、老师、课程、考试和学生状态的有效信息。
2. 用国际课程和学生成长的专业视角解释信息，而不是只转发学校原文。
3. 识别问题、风险和机会，明确哪些可以观察、哪些需要马上介入。
4. 制定并推动下一步动作，跟踪到完成或进入下一轮计划。
5. 用家长能理解的语言和固定节奏汇报，减少信息差、意外和无依据的焦虑。

已确认的对外核心表达（正式营销文案可再润色）：

> 我们不只是替家长接收信息，而是持续理解孩子、理解学校、判断问题并推动解决。家长能够知道孩子现在怎么样、哪里在进步、哪里需要介入，以及下一步由谁在什么时候完成。

### 2.5 大学前服务分层

#### A. 全程学业托管

适用于有陪读家长，或已有寄宿家庭负责基本生活照顾的学生。

主要范围：

- 学校通知和沟通协助。
- 国际课程、选课、考试和升学路径解释。
- 学习目标、课程、出勤、作业、成绩和老师反馈监督。
- 学校会议准备、参与或会后解读。
- 风险识别、学习介入和补救计划。
- 固定月报、学期复盘和家长沟通。

#### B. 全方位托管协调

适用于没有陪读家长，需要公司在学业之外承担更多协调工作的学生。

在全程学业托管基础上，可增加：

- 与寄宿家庭、宿舍或日常照顾方的必要沟通。
- 作息、出勤、校园适应和生活状态定期核对。
- 学校、学生、家长、寄宿家庭和外部服务方之间的协调。
- 失联、受伤、纪律问题或其他重大情况的应急联络与升级。
- 更高频的学生状态检查和家长安心汇报。

边界原则：

- “全方位托管协调”不自动等于法定监护、24 小时现场看护、医疗判断、心理诊断、移民法律服务或结果保证。
- 若公司实际提供监护、住宿、医疗陪同、签证/准证或紧急现场处置，应在合同中分别写明范围、负责人、时段、收费和责任边界。
- 服务名称可以表达全面负责的体验，但合同必须用可执行事项说明“负责到什么程度”。

## 4. 目标业务生命周期

### 4.1 大学前全程托管

`签约与授权 → 基线评估 → 学期目标 → 学校/学习/生活执行 → 周度检查 → 月度汇报 → 风险升级 → 学期复盘 → 升学或阶段转换`

### 4.2 大学阶段成长管理

`大学入学 → 学业与适应评估 → 专业/能力目标 → 学期行动计划 → 项目与活动 → 实习准备 → 阶段复盘 → 毕业准备`

### 4.3 实习与就业

`职业方向 → 能力差距 → 简历与材料 → 目标企业/岗位 → 投递 → 测评 → 面试 → Offer → 入职 → 雇主反馈 → 下一阶段`

## 5. 大学前全托管功能蓝图

### 5.1 服务项目与责任

每次购买全托管服务应建立独立服务项目，至少记录：

- 服务产品、服务范围、开始日期、结束日期和状态。
- 主负责人、备份负责人、协同员工和管理复核人。
- 汇报频率、家长沟通频率、响应时限和升级规则。
- 合同或课包关联、包含事项、额外收费事项和排除事项。
- 家长、学生和学校沟通授权。

### 5.2 学生基线与目标

- 当前学校、年级、课程体系、科目和考试体系。
- 英语水平、近期成绩、学习习惯、出勤和行为情况。
- 家长预期、学生个人目标、主要焦虑和成功标准。
- 学期目标、年度目标、升学目标和目标截止日期。
- 当前风险、风险原因、风险变化和恢复标准。

### 5.3 学校对接

- 学校、校区、班主任、年级主任、升学顾问、宿舍或学生事务联系人。
- 联系人的职位、联系方式、首选沟通方式和授权范围。
- 每次电话、邮件、会议、家长会和学校通知的时间线。
- 沟通主题、学校反馈、内部判断、对外摘要、下一步和截止日期。
- 材料提交、选课、考试报名、学费、家长会、升学申请等学校任务。

### 5.4 学习管理

- 各科目标、当前成绩、考试结果和趋势。
- 课程安排、出勤、作业、课后反馈和阶段报告自动关联。
- 学校学习与机构补习之间的差距和补救计划。
- 学习任务、复习计划、考试日历和老师建议。
- 连续缺勤、成绩下降、反馈缺失和未来无课自动预警。

### 5.5 生活、适应与安全

- 住宿、交通、作息、社交和校园适应观察。
- 紧急联系人、必要医疗注意事项、监护授权和可联系时段。
- 情绪或心理风险只记录必要业务信息，并设置高敏感权限。
- 失联、受伤、严重纪律问题、学校警告等重大事件独立建档。
- 每个重大事件要记录发现、通知、处置、升级、结果和复盘。

### 5.6 家长协作

- 家长待提供材料、待确认决定、待付款或待回复事项。
- 每项家长任务有截止日期、状态和提醒记录。
- 家长小程序只展示整理后的内容，不展示内部争议、员工评价或敏感原文。
- 家长请求继续进入现有工单，但重要结果同步回学生托管时间线。

- 模拟面试、职业咨询和技能培训记录。

### 6.3 机会与申请管道

### 6.4 实习与入职管理

- 实习/工作协议、开始和结束日期、岗位、主管及联系方式。
- 工作时间、地点、任务安排、考勤和阶段目标。
- 学生周报、项目成果、困难和需要公司协调的事项。
- 雇主阶段反馈、评分、改进要求和最终评价。
- 入职后 30/60/90 天回访和下一阶段规划。

## 7. 阶段汇报体系

### 7.1 报告类型

- 周度内部检查：保证没有学生被遗漏。
- 月度家长/学生报告：全托管的主要固定交付物。
- 学期报告：目标达成、趋势、风险和下一学期计划。
- 紧急事件报告：重大风险和处理结果。
- 实习阶段报告：学生表现、雇主反馈、成果和改进计划。
- 职业结果报告：申请漏斗、面试、Offer 和最终去向。

### 7.2 月报固定结构

1. 本月服务概览。
2. 公司本月完成的工作。
3. 学生的可见变化和证据。
4. 当前问题、风险及变化。
5. 学校、学习、生活或职业事务进展。
6. 下月计划和明确截止日期。
7. 需要家长或学生配合的事项。
8. 主负责人及更新时间。

### 7.3 报告生成与发布规则

- 自动汇总课程、出勤、课后反馈、学校沟通、托管活动、任务和风险。
- 学管人工编辑，不能未经确认直接把内部原文发送给家长。
- 报告需经过提交、审核、发布、撤回等状态。
- 发布时保存内容快照，底层数据后续变化不能修改历史报告。
- 记录发布人、发布时间、查看时间、查看次数、家长确认和回复。
- 未按时生成、未审核、未发布或长期未读应自动提醒。
- 现有期中/期末课程报告保持不变，并可作为托管月报的引用证据。

### 7.4 什么证据代表服务已经交付

已确认采用五段式交付证据链：

`事实证据 → 专业判断 → 介入动作 → 结果验证 → 下一步计划`

每条重要托管记录至少包含：

1. **事实证据**：学校邮件、通知、会议纪要、成绩、出勤、作业、老师反馈、学生访谈或寄宿家庭反馈。
2. **专业判断**：这件事说明什么，属于正常波动、持续观察还是必须介入。
3. **介入动作**：公司已经联系谁、安排什么、调整什么或要求学生完成什么。
4. **结果验证**：问题是否改善、任务是否完成、学校或老师是否确认、是否仍存在风险。
5. **下一步计划**：负责人、动作、截止日期和下一次检查时间。

只有原始材料而没有判断，不算完整专业交付；只有判断而没有后续动作，也不算完成闭环。

### 7.5 已确认的标准交付物

#### 入托建档包

- 学生基线评估。
- 国际课程和学校情况说明。
- 家长预期与学生目标。
- 学期目标和风险基线。
- 学校、家长、寄宿家庭及紧急联系人图谱。
- 初始 30 天行动计划。

#### 学校沟通记录

- 学校通知的中文解释和影响判断。
- 电话、邮件、会议的时间、对象和主题。
- 学校原始结论、公司判断、需家长知道的内容。
- 会后动作、负责人、截止日期和完成结果。

#### 学习进展记录

- 出勤、作业、测验、考试和老师反馈变化。
- 学生当前优势、瓶颈和近期趋势。
- 哪些问题可以继续观察，哪些需要增加课程、改变方法或联系学校。
- 每次介入前后的对比证据。

#### 风险介入记录

- 风险触发原因和严重程度。
- 发现时间、首次响应时间和通知对象。
- 介入方案、执行过程、结果和是否解除风险。
- 如未解决，必须保留下一步和再次评估日期。

#### 月度正式报告

- 本月学校、学习和生活状态概览。
- 公司本月完成事项清单。
- 学生真实进展、困难和证据。
- 已经采取的介入措施和结果。
- 下月计划、负责人、日期及家长待配合事项。

#### 学期复盘

- 学期目标完成情况。
- 成绩、出勤、学习习惯和风险趋势。
- 学校及老师综合反馈。
- 哪些方法有效、哪些需要调整。
- 下一学期目标、课程和学校事务计划。

### 7.6 什么不能单独算作完整交付

- 只转发学校邮件或微信群截图。
- 只说“老师反馈还可以”或“孩子最近不错”。
- 只安排课程，但没有说明为什么安排及效果如何。
- 只记录参加过学校会议，没有会议结论和后续动作。
- 只告诉家长存在问题，没有介入方案、负责人和时间。
- 只完成一次沟通，没有跟踪问题最终是否改善。
- 月报只是罗列活动，没有专业判断、风险和下一步。

### 7.7 用交付证据解决家长焦虑

家长焦虑通常来自“不知道”，不一定来自问题本身。家长端和正式报告应持续提供四种确定性：

1. **状态确定性**：孩子目前正常、需关注还是高风险。
2. **原因确定性**：判断基于什么学校、老师、成绩或行为证据。
3. **行动确定性**：公司正在做什么，由谁负责。
4. **时间确定性**：什么时候完成，什么时候再次更新。

即使学校尚未回复，也应向家长显示：公司何时联系、目前等待什么、下次跟进日期是什么。这样“暂无结果”仍然是一项可追踪的服务状态，而不是沉默。

### 7.8 已确认的第一版服务节奏

| 场景 | 建议交付节奏 |
| --- | --- |
| 新学生入托 | 服务开始后 7 个工作日内完成基线评估和首个行动计划 |
| 内部学业检查 | 每名全托管学生每周至少一次 |
| 无陪读学生生活状态核对 | 每周至少一次，出现风险时提高频率 |
| 学校通知 | 收到后及时登记；重要事项在 1 个工作日内完成解释和分派 |
| 学校会议 | 会前准备；会后 2 个工作日内形成纪要、判断和行动项 |
| 月度报告 | 每个自然月或固定服务月发布一份 |
| 学期复盘 | 每学期结束后发布一份，并形成下一阶段计划 |
| 普通风险 | 1 个工作日内明确负责人和行动计划 |
| 严重安全/纪律/退学等风险 | 立即内部升级，并在确认基本事实后当天通知家长 |
| 家长询问 | 先确认收到，再按约定时限给出结论或下一次更新时间 |

以上节奏作为试点期内部执行标准。正式写进销售合同和系统强制 SLA 前，再结合试点实际耗时、团队人数、服务价格、学校时区和是否提供现场生活服务进行一次容量与责任边界复核；复核只能调整公司无法稳定承担的合同数值，不改变固定检查、及时介入、月度汇报和明确下一次更新时间的核心承诺。

## 9. 权限、隐私与安全

1. 未成年学生以家长/监护人授权为核心，但仍要控制敏感信息范围。
2. 学生成年后，成绩、职业、健康和个人计划是否对家长开放，应由成年学生授权。
3. 家长、学生、老师、学管、教务、客服、财务和管理层看到的内容不同。
4. 内部记录与对外摘要必须分字段保存，不能只靠员工在一段文字里自行区分。
5. 学校和雇主材料外发要记录版本、接收对象、时间和授权依据。
6. 医疗、心理、纪律、签证和重大事件属于更高敏感度数据。
7. 所有查看、发布、下载、撤回和权限变更应写审计日志。
8. 员工离职、休假或负责人变化时，必须有托管学生交接和未完成任务清单。
9. 数据保留期限和删除能力需与现有隐私规划、合同及适用法规统一确认。

## 10. 运营规则与预警

建议形成以下自动预警：

- 全托管学生没有主负责人或备份负责人。
- 服务已开始但没有目标计划。
- 连续 7 天没有任何托管活动或下一步更新。
- 下一步动作已经逾期。
- 高风险事件在规定时间内没有升级或通知。
- 本月月报未生成、未审核或未发布。
- 家长待配合事项接近截止日期。
- 学校材料、考试、申请或签证节点即将到期。
- 大学生岗位申请在某个阶段停留过久。
- 实习开始后没有学生周报或雇主反馈。
- 负责人离职/停用但仍有活跃服务项目。

5. 现有家长工单继续运行；新时间线只接收经过定义的关键结果。
6. 新功能先用功能开关和试点学生开放，未加入试点的学生行为保持不变。
7. 数据迁移先做只读盘点和预览，再由管理员确认回填。
8. 每个阶段都要有回归测试，覆盖排课、考勤、扣课、课包、结算、老师工资、财务、报告和家长权限。

## 14. 当前优先级建议

最高优先级不是立即开发大学就业模块，而是：

1. 确认全托管服务承诺与边界。
2. 用现有字段完成学生分类和试点建档。
3. 建设服务项目、连续时间线、任务和正式月报。
4. 将全托管交付展示到家长小程序。
5. 在核心托管闭环稳定后增加大学实习与就业管道。

原因：如果没有服务范围、负责人、时间线和报告，即使先做了很多岗位字段，也仍然无法保证员工持续交付。

## 16. 讨论与决策记录

### 2026-07-13：建立全托管业务总体规划

用户提出的新业务方向：

- 大学前学生由父母交给公司，公司负责对接学校、学习和阶段汇报。
- 大学及毕业阶段延伸到实习、工作等安排，并持续提供阶段性汇报。
- 需要核对现有系统是否已经具备这些能力，并提出更完整、包含用户尚未想到事项的方案。

## 17. 系统完整落地实施方案

本节形成于 2026-07-13。状态为：`已完成工程落地设计，尚未开始代码实施`。

### 17.1 工程结论

完整落地不应作为一个大版本一次上线。原因不是功能做不出来，而是全托管同时涉及学生档案、员工责任、家长权限、敏感信息、报告发布、微信通知和现有教学财务数据；一次上线会让测试和回滚范围过大。

推荐采用六个独立纵向版本：

1. 现有数据启用与试点准备。
2. 托管主档、团队、计划、时间线和任务。
3. 正式月报、审核、发布和家长查看。
4. 学校、生活、风险、联系人和证据文件。
5. 成年学生授权、大学成长与学生端。
6. 实习就业机会、申请、面试、Offer、Placement 和雇主反馈。

每个版本都必须能单独使用、单独验收、单独回滚。未加入试点的学生继续使用现有系统，不改变排课、考勤、扣课、课包、结算、工资、财务和家长请求规则。

### 17.2 现有能力复用清单

| 子问题 | 现有代码/数据 | 落地方式 |
| --- | --- | --- |
| 学生身份 | `Student` | 继续作为唯一学生主体，不新建第二套学生表 |
| 服务类型摘要 | `Student.servicePlanType` | 作为兼容摘要保留；新服务项目成为长期主数据 |
| 风险与下一步摘要 | `academicRiskLevel`, `nextAction`, `nextActionDue`, `advisorOwner` | 试点期兼容回写，后续详情从托管模块读取 |
| 课程与学习证据 | `Session`, `Attendance`, `SessionFeedback` | 月报自动汇总，不复制原始数据 |
| 课程阶段报告 | `MidtermReport`, `FinalReport` | 作为托管报告引用证据，不改变原模型 |
| 学校申请合同收费 | `SchoolApplicationService` | 保留原流程；学校日常进度另建托管记录 |
| 家长登录与绑定 | `ParentAccount`, `ParentStudentLink`, `ParentPortalSession` | 直接复用现有身份和绑定边界 |
| 家长请求 | `Ticket` | 继续处理单次请求；关键结果可回写托管时间线 |
| 微信通知 | `MiniappNotificationOutbox` 和现有发送器 | 增加报告发布模板意图，不新建第二套队列 |
| 操作审计 | `AuditLog`, `ParentPortalAudit` | 所有写入、发布、查看和撤回继续写审计 |
| 文件存储 | 现有上传/S3能力 | 复用存储组件，新增学生托管附件元数据 |
| 功能开关 | `AppSetting` | 使用 `care_management_v1` 控制试点开放 |

不采用以下捷径：

- 不用 `Student.note` 保存全部托管历史。
- 不把托管月报塞进 `FinalReport`。
- 不把每次学校沟通都建成普通 Ticket。
- 不为家长端另建一套学生、课表、反馈和财务数据。
- 不引入新的消息队列、数据库或第三方工作流平台。

### 17.3 总体架构

```text
现有教学数据                      新增全托管领域
────────────────────             ─────────────────────────
Student ────────────────────────> CareEngagement（服务项目）
Session / Attendance ───────┐       │
SessionFeedback ────────────┤       ├── CarePlan（阶段计划）
Midterm / FinalReport ──────┤       ├── CareActivity（五段式时间线）

                                             │
                                             └── CareReportPublication

员工后台/员工小程序
       │ 写入、审核、发布
       v
```

关键边界：

- 教学数据是事实来源，全托管模块只引用和解释，不复制或重算扣课结算。
- 内部内容和家长可见内容在数据库字段上分离，不靠文字约定。
- 家长接口永远从“已发布快照”读取，不读取内部草稿。
- 所有状态变化通过服务层执行，页面和 API 不直接拼接多表写入。

### 17.5 核心数据模型

#### 17.5.1 `CareEngagement`

一名学生每购买或进入一段托管服务，建立一条服务项目。

核心字段：

- `id`, `studentId`, `programType`, `status`
- `startDate`, `endDate`
- `caseOwnerUserId`
- `scopeJson`, `exclusionsJson`
- `cadenceJson`, `slaJson`
- `baselineJson`, `currentGoalsJson`, `successCriteriaJson`
- `lastActivityAt`, `nextReportDueAt`
- `createdByUserId`, `version`, `createdAt`, `updatedAt`

约束：

- 同一学生可以同时拥有不同类型服务，例如大学成长和职业启航。
- 同一学生同一 `programType` 同时只能有一个 `ACTIVE` 项目，使用 PostgreSQL 部分唯一索引保证。
- `scopeJson` 和 `exclusionsJson` 保存服务范围快照，后续改合同不能悄悄改变历史承诺。
- `version` 用于并发更新检查。

#### 17.5.2 `CareEngagementMember`

记录每个服务项目的责任团队。

字段：

- `engagementId`, `userId`, `role`
- `isActive`, `assignedAt`, `endedAt`
- `assignedByUserId`, `note`

第一版配置：

- Jasmine：`CASE_OWNER`, `ACADEMIC_OWNER`, `SCHOOL_OWNER`, `LIFE_OWNER`
- Zhao Hongwei：`EXECUTIVE_OWNER`
- 月报审核角色在正式试点前指定；没有审核人时不得发布正式月报。

#### 17.5.3 `CarePlan`

保存每个学期或阶段的计划，不覆盖上一阶段历史。

字段：

- `engagementId`, `periodLabel`, `periodStart`, `periodEnd`
- `baselineJson`, `goalsJson`, `successCriteriaJson`, `actionPlanJson`
- `status`, `approvedAt`, `approvedByUserId`
- `createdByUserId`, `version`, `createdAt`, `updatedAt`

#### 17.5.4 `CareActivity`

这是全托管最重要的连续交付记录，严格对应五段式证据链。

字段：

- `studentId`, `engagementId`, `category`, `occurredAt`, `title`
- `sourceType`, `sourceId`, `sourceLabel`
- `factEvidence`
- `professionalJudgment`
- `actionTaken`
- `outcomeVerification`
- `nextAction`, `nextActionDue`
- `riskLevel`
- `internalNote`
- `publicSummary`
- `audience`, `publicationStatus`, `publishedAt`, `revokedAt`
- `createdByUserId`, `updatedByUserId`, `version`, `createdAt`, `updatedAt`

规则：

- `INTERNAL_ONLY` 内容不能通过家长 API 返回。
- 家长可见活动必须填写 `publicSummary`，不能直接暴露 `internalNote`。
- `HIGH` 或 `CRITICAL` 风险必须有负责人和下一步截止日期。
- 有下一步动作时，可在同一事务中创建 `CareTask`。
- 发布后修改公开内容应生成新版本或重新审核，不能静默改变家长已看到的事实。

#### 17.5.5 `CareTask`

用于“谁在什么时候做什么”，不替代 Ticket，也不依赖聊天提醒。

字段：

- `studentId`, `engagementId`, `activityId?`
- `title`, `description`, `assignedToUserId`
- `status`, `priority`, `dueAt`
- `waitingOn`, `blockedReason`
- `completionEvidence`, `completedAt`, `completedByUserId`
- `parentActionRequired`, `parentVisibleSummary`
- `version`, `createdAt`, `updatedAt`

规则：

- `WAITING_EXTERNAL` 必须有下一次跟进日期，不能无限等待学校。
- 标记 `DONE` 时必须填写完成结果或证据。
- 服务暂停后停止生成常规任务提醒，但高风险任务继续显示。

#### 17.5.6 `CareContact`

字段：

- `studentId`, `engagementId?`
- `organizationName`, `contactName`, `roleTitle`
- `phone`, `email`, `preferredChannel`
- `contactType`: SCHOOL / HOST_FAMILY / DORMITORY / EMERGENCY / EMPLOYER / OTHER
- `authorizationScope`, `isPrimary`, `isActive`, `note`

联系方式属于敏感信息，只向有托管权限的员工开放，不直接展示给任课老师或普通家长账号。

#### 17.5.7 `CareAttachment`

字段：

- `studentId`, `engagementId`, `activityId?`, `taskId?`, `reportId?`
- `category`, `filePath`, `originalFileName`, `mimeType`, `fileSizeBytes`
- `audience`, `uploadedByUserId`, `createdAt`, `archivedAt`

规则：

- 复用现有安全上传和文件健康检查。
- 下载必须验证员工权限或家长学生绑定，不能仅凭文件 URL。
- 删除业务记录时附件先归档，不立即物理删除；最终保留期限跟随隐私规划。

#### 17.5.8 `CareReport` 与 `CareReportPublication`

`CareReport` 保存可编辑工作流：

- `studentId`, `engagementId`, `reportType`
- `periodStart`, `periodEnd`, `periodLabel`
- `status`, `draftJson`, `sourceRefsJson`
- `assignedToUserId`, `reviewerUserId`
- `submittedAt`, `approvedAt`, `publishedAt`, `revokedAt`
- `version`, `createdAt`, `updatedAt`

`CareReportPublication` 保存不可变发布版本：

- `reportId`, `publicationNo`, `snapshotJson`
- `publishedByUserId`, `publishedAt`, `revokedAt`, `revokeReason`
- `firstViewedAt`, `lastViewedAt`, `viewCount`

约束：

- 同一服务项目、报告类型和报告周期只能有一份有效报告。
- 家长只读取未撤回的 `CareReportPublication.snapshotJson`。
- 报告重新发布时新建 publication，不覆盖旧快照。
- 通知使用 publication ID 去重，避免撤回重发与旧通知冲突。

### 17.7 状态机与写入边界

```text
服务项目
DRAFT ──activate──> ACTIVE ──pause──> PAUSED ──resume──> ACTIVE
  │                    │                         │
  └──cancel────────────┴──complete/cancel───────┘

报告
DRAFT ──submit──> IN_REVIEW ──approve──> APPROVED ──publish──> PUBLISHED
  ^                     │                                      │
  └────request changes──┘                                      └──revoke──> REVOKED

任务
OPEN ──start──> IN_PROGRESS ──done──> DONE
  │                  ├──waiting──> WAITING_EXTERNAL ──resume──> IN_PROGRESS
  │                  └──block────> BLOCKED ──resume───────────> IN_PROGRESS
  └──cancel───────────────────────────────────────────────────> CANCELLED
```

所有状态变更必须：

- 验证当前状态是否允许转换。
- 验证操作者权限和责任关系。
- 使用 `version` 或 `updatedAt` 做乐观并发控制。
- 在一个数据库事务中写业务数据、摘要字段和审计。
- 返回明确的冲突信息，不能后保存的人静默覆盖先保存的人。

- `canViewCareUpdates`
- 继续复用现有 `canViewReports`

### 17.12 核心业务流程

#### 17.12.1 新学生入托

```text
选择学生
  -> 创建 DRAFT 服务项目
  -> 选择服务层级与范围
  -> 指定 Jasmine / Zhao Hongwei 及角色
  -> 完成基线、目标、联系人、权限
  -> 系统预览将创建的节奏和首批任务
  -> 管理员确认激活
  -> 创建 30 天计划、周检查和首份月报截止日期
  -> 写审计
```

激活前缺少服务范围、负责人、开始日期或家长可见权限时必须阻止激活。

#### 17.12.2 学校通知或会议

```text
上传/登记学校事实
  -> 选择类别与来源
  -> 填专业判断
  -> 判断风险等级
  -> 填介入动作
  -> 创建负责人和截止日期
  -> 生成家长摘要草稿
  -> 审核后发布
  -> 后续验证结果并关闭任务
```

#### 17.12.3 月报生成与发布

```text
按报告周期锁定学生与服务项目
  -> 批量读取课程、出勤、反馈、活动、任务、风险、既有报告
  -> 生成确定性草稿和来源引用
  -> Jasmine 编辑并提交
  -> 审核人核对事实与家长口径
  -> 批准
  -> 事务内创建不可变 Publication 快照
  -> 写审计
  -> 排入微信报告通知
  -> 家长查看并写 ParentPortalAudit
```

第一版不使用 AI 自动写结论；先用结构化汇总和人工判断。后续 AI 只生成有来源引用的草稿，永远不能自动发布。

#### 17.12.4 风险介入

```text
发现风险
  -> 建 CareActivity + riskLevel
  -> HIGH/CRITICAL 强制负责人、截止日期、通知策略
  -> 创建 CareTask
  -> 管理层工作台置顶
  -> 记录介入动作
  -> 验证结果
  -> 解除、降级或继续升级
```

严重事件的内部升级不等于未经核实立即向家长发送全部原文；先确认基本事实，再按已确认时限通知。

### 17.13 提醒与异常工作台

第一版不新建独立消息基础设施，使用实时查询和现有通知队列。

内部异常规则：

- `ACTIVE` 服务项目连续 7 天无活动。
- 当前没有 `CASE_OWNER` 或责任成员已停用。
- 任务逾期或 `WAITING_EXTERNAL` 没有下次跟进日期。
- `HIGH/CRITICAL` 风险没有负责人或介入动作。
- 月报到期未创建、未提交、未审核或未发布。
- 已发布报告长期未读。
- 家长配合事项临近截止日期。

计算方式：

- 88 名学生规模下先通过索引查询实时计算，不建立 `CareAlert` 表。
- `CareEngagement.lastActivityAt` 和 `nextReportDueAt` 用于快速筛选。
- 每晚只读审计脚本检查摘要时间是否与真实活动一致，发现漂移只报告，不自动改数据。
- 需要家长微信提醒时继续写 `MiniappNotificationOutbox`。

### 17.15 数据迁移与试点启用

迁移原则：只新增，不破坏现有表和数据。

步骤：

1. 新增枚举、表、外键和索引，所有对现有表新增字段先允许空值。

- 关闭 `care_management_v1` 后隐藏新入口并停止新写入。
- 新数据保留，不删除、不回滚现有学生字段。
- 已发布家长报告即使功能关闭，也由管理员决定是否继续只读可见或统一撤回。

### 17.17 推荐代码组织

新领域服务保持少而明确：

```text
lib/care-management.ts        状态机、服务项目、成员、活动、任务
lib/care-access.ts            员工、家长、成年学生权限
lib/care-report.ts            周期、汇总、审核、发布快照
```

不要把每个模型拆成一个服务文件，也不要把所有逻辑放进页面组件。页面负责展示，Route Handler 负责输入输出，`lib/care-*` 负责业务不变量和事务。

复杂状态机和报告发布管道应在 `lib/care-management.ts` 与 `lib/care-report.ts` 顶部保留简短 ASCII 图，并在状态变化时同步更新。

### 17.18 索引与性能

必要索引：

- `CareEngagement(status, caseOwnerUserId, nextReportDueAt)`
- `CareEngagement(studentId, status)`
- `CareEngagementMember(userId, isActive)`
- `CareActivity(engagementId, occurredAt)`
- `CareActivity(studentId, publicationStatus, occurredAt)`
- `CareTask(assignedToUserId, status, dueAt)`
- `CareTask(engagementId, status, dueAt)`
- `CareReport(engagementId, reportType, periodStart, periodEnd)`
- `CareReport(status, reviewerUserId, periodEnd)`
- `CareReportPublication(reportId, publishedAt)`

查询原则：

- 工作台一次批量查询计数和摘要，禁止每个学生单独查询活动和任务。
- 报告生成对课次、反馈、活动和任务按周期批量读取。
- 时间线和报告列表分页，不一次加载全部历史。
- 常用筛选字段用关系字段或枚举，不把状态和截止日期藏进 JSON。
- 88 名学生规模无需新增缓存或搜索服务；先保持 PostgreSQL 单一事实来源。

### 17.19 失败场景与处理

| 失败场景 | 预防/处理 | 用户看到什么 |
| --- | --- | --- |
| 两人同时编辑月报 | `version` 乐观锁 | 提示内容已更新，重新加载后合并 |
| 同一月份重复生成报告 | 数据库唯一约束 | 返回已有报告入口 |
| 发布事务成功但微信失败 | 报告保持已发布，通知队列重试 | 页面显示已发布；后台显示通知待处理 |
| 家长无权限访问报告 | 绑定、权限、publication 三重校验 | 403/无权查看，不泄露报告是否存在 |
| 报告撤回后旧页面缓存 | 父端接口禁用公开缓存并实时检查 `revokedAt` | 显示报告已撤回 |
| 学校一直不回复 | `WAITING_EXTERNAL` 强制下次跟进时间 | 家长看到等待状态和下次更新时间 |
| Jasmine 账号停用 | 工作台检测活跃项目无有效负责人 | 管理层看到红色交接异常 |
| 服务暂停仍生成月报提醒 | 节奏计算过滤 PAUSED/COMPLETED/CANCELLED | 不产生常规逾期提醒 |
| 上传证据文件丢失 | 文件健康检查和归档状态 | 员工看到附件异常，不能发布为有效证据 |
| 内部备注误发家长 | 独立字段、DTO白名单、发布预览和测试 | 家长永远只收到 publication snapshot |
| 新模块影响课包结算 | 新服务层禁止写 Package/Txn/Settlement | 发布前回归测试发现任何数量或金额变化 |

任何“无测试、无错误处理、且用户无提示”的失败路径都不得进入生产。

### 17.21 上线验收指标

功能验收：

- 100% 试点学生有 ACTIVE 服务项目和明确责任团队。
- 100% 试点学生有当前阶段计划、下一步和下次报告日期。
- 家长可见内容与内部内容字段和接口完全分离。
- 月报可生成、编辑、审核、发布、查看、撤回和追踪阅读。
- 高风险、无更新、任务逾期和月报逾期可在工作台识别。

非回归验收：

- 学生、课包、课次、考勤、结算、工资、发票、收据数量和金额无意外变化。
- 现有普通课程学生页面和家长小程序体验不变。
- 现有期中/期末报告和反馈发布逻辑不变。
- 生产迁移、构建、PM2、健康检查和唯一 cron 验证通过。

运营验收：

- 连续运行一个完整月报周期。
- 试点学生没有因负责人不清而遗漏。
- Jasmine 能在系统中完成每周检查和月报，不依赖额外表格。
- 家长能够回答：孩子当前状态、判断原因、公司行动和下一次更新时间。
- 记录每名学生实际服务耗时，为负责人容量和价格复核提供依据。

### 17.22 明确不在第一批范围

- 法定监护、24 小时现场看护、医疗/心理诊断和移民法律服务：需先完成合同与资质边界。
- 自动读取学校邮箱或聊天记录：第一批由员工登记，避免授权和隐私范围扩大。
- AI 自动判断风险或自动发布月报：先建立结构化证据和人工审核标准。
- 重做现有 Ticket、学校申请合同、排课、财务或老师工资：全部继续复用。
- 建立公开岗位市场或雇主招聘平台：职业模块先服务现有学生和现有机会。
- 一次性开放全部 88 名学生：先试点 5-10 名，完成一个月报周期后扩大。
- 对成绩、升学、Offer 或就业结果作系统性保证：交付标准是专业过程、及时介入和可验证行动，不是不可控结果保证。

### 18.4 家长可见范围建议

推荐采用“默认可见、条件可见、内部不可见”三层，而不是让员工每次临时判断。

#### A. 默认向家长可见

这些内容直接服务于降低家长焦虑：

- 当前服务类型、服务状态、主要负责人和最近更新时间。
- 当前总体状态：正常、需关注、高风险。
- 本阶段公开目标和本月重点。
- 学校重要通知的中文解释、影响和公司下一步。
- 学校会议的家长版纪要、学校结论和行动项。
- 课程、出勤、作业、测验、考试和老师反馈的整理摘要。
- 学生正在进步的方面、当前瓶颈和可改善方向。
- 已经采取的介入措施及验证结果。
- 下一个动作、负责人、截止日期和下一次更新时间。
- 需要家长配合的事项和截止日期。
- 已审核发布的月报、学期报告和必要事件报告。
- 公司本月已完成的服务事项清单。

#### B. 满足条件后向家长可见

以下内容需要先确认事实、隐私和第三方信息：

- 学校原始邮件、通知截图和会议附件：去除其他学生、老师私人联系方式和无关第三方信息后才可发布。
- 寄宿家庭或宿舍反馈：只发布与学生安全、适应、作息和学业有关的整理摘要。
- 生活、健康或情绪问题：只发布家长为履行监护或配合责任所必需的事实、风险和行动，不发布无关私密细节。
- 纪律、安全、失联、受伤等重大事件：确认基本事实后按风险流程发布，不发送未经核实的传言。
- 成年学生的学业、生活、健康和职业信息：必须叠加学生本人授权。
- 老师给管理层的专业判断：转写成家长能理解的公开摘要后发布，不直接复制内部措辞。

#### C. 内部不可向家长展示

- 未审核的草稿、内部备注和员工之间的讨论。
- 对员工、老师、学校或家长的内部评价。
- 尚未核实的投诉、猜测、传言和责任判断。
- 内部风险评分细则、敏感标签和管理层升级讨论原文。
- 其他学生及其他家庭的信息。
- 学校、老师、寄宿家庭员工的私人联系方式，除非取得授权且业务必须。
- 老师工资、合作方结算、公司成本、利润、内部审批和人员绩效。
- 法律意见、医疗诊断或心理判断等公司无资质作出的内容。
- 已撤回报告和已经撤销公开的活动版本。

### 18.5 家长端展示原则

家长端不应把所有原始材料直接堆给家长，而应固定回答：

1. 孩子现在怎么样？
2. 我们依据什么作出这个判断？
3. 公司已经做了什么？
4. 结果有没有改善？
5. 下一步由谁在什么时候完成？
6. 家长需要配合什么？

推荐首页只显示摘要；点击后再查看公开时间线和报告。风险状态使用正常、需关注、高风险三个家长可理解级别，内部 `CRITICAL` 等处置等级不直接作为生硬标签展示。

### 18.6 无陪读学生生活协调范围

无陪读学生仍以“学业托管”为核心，生活协调的目标是保证安全、稳定和不影响学习，而不是代替寄宿家庭提供日常照料。

#### 第一版默认包含

1. **每周学生状态核对**
   - 本周是否正常到校和上课。
   - 作息、睡眠、饮食是否出现明显影响学习的问题。
   - 与寄宿家庭、宿舍、同学和学校的适应情况。
   - 是否有生病、受伤、失联、纪律或安全问题。
   - 下周重要课程、考试、学校活动和待办。

2. **寄宿家庭或宿舍协调**
   - 建立主要联系人和紧急联系方式。
   - 对影响学习、安全和校园出勤的问题进行沟通。
   - 正常情况下每月至少一次状态核对；出现问题时按风险提高频率。
   - 记录事实、双方说法、公司判断、行动和结果。

3. **学校出勤与纪律协同**
   - 跟进无故缺勤、迟到、学校警告和行为问题。
   - 区分偶发问题和持续风险。
   - 需要介入时联系学校、学生、寄宿家庭和家长。

4. **重要日程和行政提醒**
   - 学校会议、考试、选课、活动、材料和重要截止日期。
   - 学生需要自己完成的事项进入任务清单。
   - 签证/准证仅做材料和到期协调提醒，不提供移民法律意见。

5. **异常和紧急协调**
   - 失联、受伤、严重生病、纪律、安全或可能退学等情况立即内部升级。
   - 确认基本事实后当天通知家长。
   - 协调学校、寄宿家庭、家长和必要外部资源。
   - 保存处理过程、结果和复盘。

6. **家长安心汇报**
   - 月报增加“生活与适应”栏目。
   - 没有异常时也明确说明本月完成了哪些核对。
   - 有问题时说明事实、判断、介入、结果和下一次检查日期。

7. **医疗预约及现场陪同**
   - 协助选择合适的医疗机构、预约时间和准备基本资料。
   - 在合理安排下提供现场陪同、语言沟通、流程协调和就诊结果记录。
   - 及时向家长同步已确认的事实、医生建议和后续安排。
   - 公司不作医疗诊断、不替代医生决定、不擅自决定用药；涉及未成年人的重大医疗决定仍由家长/法定监护人或适用的紧急机制处理。

8. **机场接送和重要交通**
   - 协调抵达、离境、转学、搬家、医疗或重要学校活动所需交通。
   - 根据学生年龄、路线和风险决定安排司机接送、员工陪同或其他合适方式。
   - 记录航班/行程、接送人、联系方式、确认状态和异常处理。

9. **寄宿家庭筛选、更换和走访**
   - 收集寄宿家庭信息，核对基本条件、位置、通勤和学生实际需要。
   - 协调沟通、必要走访、入住准备、问题反馈和更换流程。
   - 保存选择依据、家长确认、已知风险和后续检查记录。
   - 公司进行合理筛选和协调，但不对独立第三方未来所有行为作绝对保证。

10. **假期住宿与临时照护协调**
    - 根据学校假期、家长安排和学生年龄协调住宿、活动及临时照护方案。
    - 核对时间、地点、联系人、交通、紧急安排和家长确认。
    - 涉及公司直接提供照护时，必须另行明确现场负责人、时段、人数、安全规则和责任边界。

11. **签证/准证材料行政协助**
    - 提醒到期时间、整理材料清单、协助填写行政资料、预约和递交协调。
    - 记录材料状态、截止日期、待家长/学生完成事项和官方结果。
    - 不提供移民法律意见，不保证审批结果；复杂或有争议的情况转交有资质的专业机构。

以上五项已经用户确认“包含”。包含的是公司提供的合理协调、沟通、安排和必要人员支持；医疗费、药费、交通费、机票、住宿费、寄宿费、签证官方费用及其他第三方实际收费，原则上由家长承担，除非具体合同明确写明费用已经包含。

#### 第一版默认不包含

- 24 小时实时定位或全天候现场值守。
- 每日叫醒、逐餐监督、洗衣、清洁和日常家务管理。
- 学生日常现金、银行卡、消费和零花钱代管。
- 法定监护责任和替家长作出法律决定。
- 医疗诊断、用药决定和心理诊断。
- 医疗诊断、用药决定、移民法律意见和审批结果保证。
- 不限次数、不限距离、不限时长的交通、陪同、住宿和现场照护。
- 对学生成绩、安全或行为作绝对结果保证。

#### 需要按学生单独启用或明确范围

- 高频每日状态确认或特殊行为监督计划。
- 非工作时间紧急现场支持。
- 公司直接提供的现场临时照护。
- 超出合同合理次数、距离或时长的高频交通、医疗陪同、走访和行政协助。

这些服务必须记录启用原因、开始和结束时间、频率、负责人、费用规则和紧急联系人，不能只在微信聊天中口头扩大责任。

#### 高频每日状态确认是什么意思

它不是 24 小时监控，也不是持续 GPS 定位。它是一项短期、轻量的安全与纪律确认：

- 学生每天在约定时间确认是否已到校。
- 确认是否已安全回到住处。
- 确认当天是否出现生病、受伤、失联、纪律或紧急问题。
- 必要时确认次日重要考试、材料或行程是否准备完成。
- 系统只把未确认、超时或异常答案推给负责人处理。

建议启用场景：

- 刚到新加坡或刚更换学校/寄宿家庭。
- 年龄较小、独立生活能力尚未稳定。
- 近期出现缺勤、迟到、失联、作息、健康或纪律风险。
- 特殊考试、医疗恢复或重大事件后的观察期。
- 家长提出合理要求且服务项目明确包含。

建议按 7-30 天设置开始和结束日期，每周复核是否继续；稳定后恢复每周状态核对。普通稳定学生不默认每日打卡，避免形成过度监控和无法持续的人力承诺。

#### 非工作时间紧急支持分级

用户确认非工作时间现场支持“分情况”。建议按以下标准处理：

1. **一级紧急：立即响应**
   - 人身安全威胁、严重受伤或疾病、失联、暴力、警方/医院介入、严重纪律或可能被学校即时停学/退学。
   - 公司立即远程响应，优先联系当地紧急服务、学校、寄宿家庭和家长。
   - 是否派人现场根据地点、人员安全、事件性质和当时可用人员决定，不能延误拨打紧急服务。

2. **二级紧急：及时协调**
   - 不危及生命但不能合理等到下一个工作日的问题，例如临时无住处、重要交通中断、轻中度疾病需要就医、寄宿关系突然恶化。
   - 先远程协调可用资源；确有必要且人员条件允许时安排现场支持。

3. **三级一般事项：工作时间处理**
   - 普通材料、日常交通调整、非紧急寄宿意见、一般学习和生活问题。
   - 登记后在下一个工作日处理，不启动非工作时间现场支持。

在公司建立正式轮值、联系电话和到场 SLA 前，对外应承诺“非工作时间紧急协调响应”，不承诺任何地点固定分钟数到场。现场支持是否包含额外费用，可按事件等级、时间、距离和实际投入在合同中明确。

### 18.7 无陪读生活检查在系统中的实现

第一版生活协调记录复用 `CareActivity(category=LIFE)` 和模板化字段：

- 到校与课程状态。
- 作息与基本生活状态。
- 住宿与关系适应。
- 身体与情绪自述，仅记录必要事实，不作诊断。
- 本周事件和风险。
- 已采取行动。
- 下次检查日期。
- 家长可见摘要。

出现高风险时，同一事务创建 `CareTask`；需要附件时关联 `CareAttachment`；月底自动汇总到月报“生活与适应”栏目。这样保留完整证据链，又不为第一版增加重复模型。

如果后续确认启用高频每日状态确认，再增加轻量 `CareCheckIn`，避免每天产生大量普通时间线记录：

- `studentId`, `engagementId`, `checkDate`

### 21.11 大学阶段服务与大学前服务的差异化规划

2026-07-14，用户指出目前大学阶段在系统中仍与大学前使用相同流程，并提出大学阶段应主要围绕学业、实习就业或研究生准备。真实代码检查确认该判断准确。

当前系统真实情况：

- 已有 `UNIVERSITY_GROWTH`（大学阶段成长管理）和 `CAREER_LAUNCH`（实习与就业支持）两个项目类型。
- 但四种项目类型目前共用同一组 `CARE_SCOPE_OPTIONS`，创建任何项目时都会默认勾选学业、学校沟通、医疗、交通、寄宿家庭、假期照护和签证协助。
- 阶段计划、跟进、待办和证据附件也使用同一套通用界面；只有活动类型中已有一个通用的“升学/职业”类别。
- 系统尚没有大学课程与学分、GPA、挂科或学术警告、研究生申请节点、实习求职申请、面试、Offer、实习评价等专用数据和工作流。
- 因此目前的大学阶段只是“名称可选、通用记录可用”，还没有形成真正不同的大学服务产品。

确认的业务方向应当是大学阶段三条主线，而不是复制大学前全托管：

1. **大学学业管理**：保证学分、成绩、毕业进度和学习能力。
2. **研究生准备**：从方向判断、背景提升到申请、Offer 和最终入学决定。
3. **实习与就业**：从职业方向、材料准备到申请、面试、Offer、入职和实习反馈。

生活、住宿、医疗、交通和签证仍可提供，但应成为按需附加服务，不应在大学项目中默认开启。大学生通常已经成年，系统还必须把学生本人放到服务关系中心；家长能看什么不能只沿用未成年阶段规则，应增加学生授权和按栏目控制的可见范围。

#### A. 大学学业管理

每个学期应记录：

- 学校、专业、学位、年级、预计毕业时间和当前培养要求。
- 本学期课程、课程学分、课程难度、考核构成和关键截止日期。
- 作业、测验、期中、期末、论文和补考节点。
- 当前 GPA、目标 GPA、已完成学分、剩余学分及毕业要求差距。
- 出勤、迟交、挂科风险、学术警告、重修和延期毕业风险。
- 与导师、教授、学校 Academic Advisor 的沟通及结论。
- 学习支持动作，例如学习计划、辅导安排、Office Hour、写作支持和考试复习。

推荐的阶段节奏：开学建学期计划，每两周检查一次关键课程和截止日期，期中做风险复盘，考试前做备考计划，出分后完成学期总结。没有风险时不需要像未成年学生一样高频每日打卡。

#### B. 研究生准备

每名学生应建立独立的研究生准备路径：

- 目标入学年份、国家、学校、专业和职业方向。
- 申请项目长名单、短名单、冲刺/匹配/保底层级和选择理由。
- 先修课、GPA、语言、GRE/GMAT、科研、实习、作品集等差距评估。
- 背景提升计划及每一项完成证据。
- 推荐人确认、推荐信状态、个人陈述、简历、作品集和成绩单准备状态。
- 每个项目的开放日期、截止日期、提交、面试、补件、Offer、拒绝、奖学金和最终决定。
- 多个 Offer 的课程、费用、地点、就业结果和风险比较。

研究生准备不能只用普通待办列表。后续系统应有项目级申请管道，使管理者一眼看到“尚未开始、准备材料、待提交、已提交、面试、Offer、拒绝、已接受”。

#### C. 实习与就业

实习就业路径应记录：

- 职业方向、目标行业、岗位、城市、工作资格和可开始日期。
- 能力盘点、技能差距、项目经历和补强计划。
- 简历、LinkedIn、求职信、作品集和面试故事库的版本与审核状态。
- 公司、岗位、职位链接、申请渠道、内推人、截止日期和负责人。
- 网申、测评、笔试、各轮面试、Offer、拒绝和跟进状态。
- 面试准备记录、反馈、失败原因及下一轮改进动作。
- Offer 薪资、地点、工作内容、签证、发展空间和接受决定。
- 实习开始后的出勤、主管反馈、阶段目标、转正可能性和最终评价。

推荐管道为：`目标机会 -> 准备申请 -> 已申请 -> 测评/笔试 -> 面试 -> Offer -> 已接受 -> 已入职/实习完成`，并保留 `暂停、拒绝、学生撤回` 等结果。系统应该同时提供机会数量、有效申请数、面试率、Offer 数和最终去向，而不是只统计写了多少条跟进记录。

#### D. 大学阶段报告应回答的问题

大学阶段报告不应继续使用大学前“学校、生活、家长沟通”作为主要栏目。建议按学生实际选择的主线动态组成：

- 学业：本期课程和成绩怎样，是否影响 GPA 或毕业，下一阶段必须完成什么。
- 研究生：目标是否清楚，差距补到哪里，各申请项目当前处于什么状态。
- 实习就业：本期完成了哪些材料和申请，获得哪些反馈，下一步如何提高转化。
- 风险：有无挂科、逾期、学术诚信、签证、毕业、求职窗口或心理状态风险。
- 专业判断：团队为什么这样判断，而不只是罗列发生过的事情。
- 下一阶段：明确学生本人、顾问和家长各自需要完成的动作与日期。

报告对象也需要区分：大学生本人查看完整行动计划；家长只查看学生授权且已经审核发布的栏目；内部团队保留敏感判断、雇主反馈和未经确认的信息。

#### E. 推荐系统落地顺序

大学阶段功能不能直接塞进当前通用页面一次完成，建议保持增量和隔离：

1. 先让服务类型控制默认服务范围：大学前、大学学业、研究生准备、实习就业分别显示各自适用选项，同时允许人工增减。
2. 为大学项目增加“大学档案、当前主线、学期、目标毕业时间、学生授权范围”，不修改现有 `Student` 和教学财务流程。
3. 建设大学学期与课程里程碑，支持 GPA、学分、考核节点和学术风险。
4. 建设研究生项目申请管道，管理学校/专业/材料/截止日期/申请结果。
5. 建设实习就业机会管道，管理职位、申请、测评、面试、Offer 和实习评价。
6. 最后让正式月报根据项目主线自动组合栏目，并分别发布给学生本人和经授权的家长。

本节方向已于 2026-07-14 获得用户确认并开始实施。近期正在推进的全托管正式月报不能把大学阶段硬套进大学前模板；开发月报前应先完成大学三条主线的最小字段和授权规则。

### 21.14 业务重心、家长价值与正式报告落地（2026-07-16）

#### 业务重心的最终确认

未来两年的主产品不是大学求职系统，而是大学前学生的长期学业与全方位托管。大学阶段保留轻量服务：按重大事项、月度、阶段或学期形成可修改、可审核、可发布给家长的报告；暂不优先建设复杂的研究生申请和就业管道。

大学前产品的核心价值是把家长无法持续完成的专业工作接住：理解国际课程和学校规则、追踪学习状态、识别风险、协调学校和老师、推动学生行动，并把事实、专业判断、已经采取的动作和下一步清楚反馈给家长。系统追求的是通过持续交付形成长期信任和自然续费，不采用制造焦虑、夸大风险或隐瞒信息的方式建立依赖。

#### 家长真正需要得到的五个答案

每一次正式沟通都应让家长明确：

1. 孩子现在真实处于什么状态，有哪些事实证据。
2. 哪些表现正常，哪些问题值得关注，风险等级是什么。
3. 团队已经做了什么，学校、老师或学生给了什么反馈。
4. 接下来由谁在什么日期前完成什么动作。
5. 哪些事项需要家长决定或配合，哪些事项暂时不需要家长介入。

家长看见的不是内部工作流水账，而是“结论、证据、判断、行动、下一步”。没有新风险时也要明确说明“目前稳定、证据是什么、下一次检查点是什么”，避免只有出问题才沟通。

#### 大学前服务分层

- `学业管理`：课程规划、学习进度、老师反馈、考试与作业节点、学业风险、补习安排和阶段复盘。
- `学校协调`：学校邮件、家长会、导师沟通、选课与升学节点、学校要求和结果跟进。
- `生活协调`：仅对全方位托管或合同约定学生启用，包含医疗预约及现场陪同、机场接送和重要交通、寄宿家庭筛选/更换/走访、假期住宿与临时照护、签证或准证材料行政协助。
- `风险干预`：出勤、成绩、行为、身心状态、住宿安全、签证和紧急事项；高风险必须升级，不等月报。
- `家长沟通`：正式报告、重大事项通知、需要家长决策的行动和确认收到。

“高频每日打卡”不作为所有学生的默认承诺。它只适用于刚到新加坡、近期失联、健康/行为/住宿风险较高，或合同明确约定的短期情形；应记录打卡目的、频率、开始和结束日期，风险解除后降频，避免把低价值消息数量当成交付。

非工作时间紧急现场支持按事件分级：涉及人身安全、急诊、警方、失联、住宿安全或当天无法延后的重大交通，可启动紧急支持；普通学校咨询、材料提醒和可延至工作日处理的事项不属于紧急现场支持。每次启动都需要记录事实、批准人、行动、费用归属和闭环结果。

#### 什么算服务已经交付

服务交付不能只靠员工写一句“已跟进”。至少应有一类真实来源：

- 已完成课程、出勤记录和老师课后反馈。
- 学校邮件、会议纪要、成绩单、评估或正式通知。
- 与学校、寄宿家庭、学生或家长的确认记录。
- 已完成待办及结果，例如预约完成、交通完成、材料提交、问题关闭。
- 现场服务照片、文件或其他附件；涉及隐私的证据只保留内部，家长报告写核验结论。
- 一条结构化托管跟进，至少包含事实证据、专业判断、采取行动、结果验证和下一步。

报告生成可以从这些来源自动汇总，但自动生成的“请负责人补充”占位文字不能提交。没有任何课程、反馈、跟进或附件来源时，系统必须阻止提交。

家长默认不可见：内部备注、未核实判断、员工讨论、第三方个人资料、寄宿家庭敏感信息、医疗原始文件、学生向团队说明且依法/依约应保密的内容、尚未批准或已撤回报告。遇到安全风险、法律义务或必须由监护人知情的事项，按照升级规则处理，不以一般隐私设置阻止必要通知。

### 21.16 全托管专业运营工作台 UI 重构（2026-07-17）

本轮设计原则：

- 全托管是高频内部运营工具，不做营销式大标题和大面积装饰卡片，采用紧凑、安静、便于扫描的专业工作台。

1. 佣金按公司实际收到且不含退款、第三方费用、代垫款和适用税费的净服务款计算；未收款不结佣。
2. 建议首年首次成交 15%，续约降至 5%；同一家庭新增课时是否结佣应在渠道协议中单独写明。
3. 分期订单按每期实收款结佣，不在签约时一次性支付全年佣金。
4. 发生退款、拒付或合同取消时，未结佣部分停止，已结佣部分按渠道协议冲回或从后续佣金抵扣。
5. 渠道不得自行承诺价格、赠课、成绩、录取、24 小时到场或超出合同范围的服务；所有报价使用公司统一报价单。
6. 佣金不覆盖第三方交通、医疗、住宿、签证官方费、现场供应商费和公司临时代垫。

#### Go / No-Go 毛利线

- 单生学业托管扣渠道佣金后，托管净收入低于 S$9,000/年时不再批准额外折扣。
- 无陪读协调附加费扣佣后低于 S$6,500/年时，不包含任何固定现场小时；现场服务单独计费。
- 首月必须记录每名学生的托管人力小时。按内部完全人力成本计算后，如果单生托管预计毛利率低于 40%，下一批渠道价上调或缩减服务范围，不继续用赠课掩盖成本。

### 21.22 签约、渠道合作与家长安心闭环落地（2026-08-05）

用户确认按既定规划执行，并要求把渠道合作、签字、家长随时看进度及降低焦虑的机制完整落地。本轮采用无数据库迁移的受控上线方案，避免在首批家庭上线前引入高风险结算模型变更。

已落实：

- 普通学费协议可附加双语《全程托管服务附件》，一次签署时冻结项目类型、服务范围、排除项、补习费与托管费拆分、服务期间、每周复核、每月报告、交付渠道、S$300 紧急代垫上限、家长/学生配合、学校及第三方沟通、资料使用和责任边界。
- 家长签字页明确一次签署同时覆盖学费协议和全托管附件；签署结果继续保留版本、签名、时间、PDF 和发票审计链。
- 渠道名称和佣金比例保存为合同内部商务快照并进入审计事件，但绝不出现在家长协议或家长接口。合同工作台显示按合同总额计算的暂估佣金及公司留存，并明确财务只按实际到账的合格净服务收入结算。
- 形成 A4 双语《全程托管渠道合作及佣金协议模板》，包含 90 天线索保护、标准渠道价、首年 15%/续约 5%、实收结佣、月结、退款冲回、统一报价、禁止越权承诺、家长交接、投诉、资料保护、审计和签字页。
- 形成 A4 双语《全程托管家长授权与入托确认表》，覆盖六个家长核心问题、学校/老师/寄宿及外部服务方沟通授权、家长可见范围、成年学生同意、紧急联系人、S$300 代垫上限、更新偏好、资料告知和双方签字。
- 家长小程序进度页升级为“安心看板”，固定回答“孩子现在怎么样、最近做了什么、下一步做什么、下次何时更新”，并显示负责人、签约服务范围、最近正式动态、家长待办及经过核实且允许披露的开放风险。重大事项承诺主动联系，不等待月报。
- 家长接口只读取 PUBLISHED 且面向家长的活动、已发布报告、家长可见任务与风险摘要；不读取内部笔记、内部事实判断、内部价格或渠道佣金。
- 后台项目新增七项启动门槛：全托管协议已签、家长绑定且可看报告、开始日期、范围、总负责人、月报审核人和首期计划。新的 DRAFT 项目缺一项时，服务层阻止切换 ACTIVE；暂停后恢复不追溯阻断既有项目。
- 合同签完后，工作台直接提示完成家长绑定并进入项目启动门槛，避免销售、财务和交付断链。
- 新增《全程托管上线执行手册》，固定渠道价格、签字顺序、家长六问、四周日历、完整演练、Go/No-Go 和首月经营复盘口径。

首批渠道价格正式采用标准年费 S$34,800 / S$40,800 / S$48,800 / S$56,800，对应 150 / 200 / 250 / 300 小时；无陪读协调和共享课时池第二名孩子托管费均为 S$7,800。渠道订单不叠加直营首批优惠，250/300 小时仍为评估后报价。

法律边界不变：现有模板是可执行的商业和流程底稿，不替代新加坡律师、税务和 PDPA 专业复核；正式签约前需完成专业审阅。
